# EPIC-10: Learning Documents

**Backlog ID:** EPIC-10  
**Issue type:** Epic (`type:epic`)  
**Parent:** None  
**Depends on:** EPIC-03, EPIC-04

**Roadmap stage:** Stage 8 - Documents  
**Outcome:** Super Admin can upload and manage approved document formats in R2; users can view documents according to access level without an application-level download action.  
**Dependencies:** EPIC-04, EPIC-03  
**Enables:** Complete Phase 1 learning library

## Epic Goal

Provide secure document viewing with metadata, file validation, private object access, and a clear distinction between viewing and a platform-provided download feature.

## Features

| ID | Feature | Result / completion evidence | Related user stories |
|---|---|---|---|
| F10.1 | Document metadata | Metadata accurately describes stored objects and access settings. | US-10.1, US-10.3 |
| F10.2 | R2 upload | Approved file formats are privately stored with server-generated keys. | US-10.1 |
| F10.3 | Admin management | Super Admin can maintain metadata and safely remove documents. | US-10.3 |
| F10.4 | Access-controlled viewing | Public, authenticated, and admin-only access is enforced. | US-10.2 |
| F10.5 | Short-lived object access | Object retrieval is issued only after authorization and expires. | US-10.2, US-10.3 |
| F10.6 | No application download button | UI provides view/open behavior only and documents browser-level limitations. | US-10.2 |

Every feature issue has parent `EPIC-10`; each story names one primary feature parent and may reference related feature IDs.

## User Stories

### US-10.1: Upload a Validated Document

**Backlog ID:** US-10.1  
**Issue type:** User Story (`type:user-story`)  
**Parent:** F10.2  
**Related feature IDs:** F10.1, F10.3  
**Depends on:** EPIC-03, EPIC-04

#### Description

As a Super Admin, I want to upload approved document formats so that users can access learning material stored privately in R2.

#### Action Items

- Validate uploaded content and metadata before accepting a document.
- Keep object storage credentials and object-key selection on the server.

#### Tasks

- [ ] Add document metadata migration and server-generated R2 key convention.
- [ ] Validate approved extension, MIME/signature where feasible, size, and safe filename.
- [ ] Upload privately and persist metadata only after successful storage.
- [ ] Define cleanup for partial upload/persistence failure and deletion.
- [ ] Add protected admin upload form and upload success/failure tests.

#### Implementation Steps

1. Add document metadata migration and R2 object-key strategy.
2. Validate extension, MIME/signature where feasible, size, and safe filename.
3. Upload server-side to private R2 location.
4. Persist metadata only after successful storage.
5. Add cleanup on failed metadata persistence and deletion workflow.
6. Add admin form with access level/category fields.

#### Acceptance Criteria
- Only Super Admin can upload.
- Unsupported format, invalid size, and missing metadata are rejected.
- Stored object key is generated by the server and does not trust the filename.
- Document metadata references the correct object and uploader.
- R2 credentials never reach browser code.

#### Test Scenarios
- Each supported format passes valid-file validation as configured.
- Extension/MIME mismatch is rejected.
- Oversized file is rejected before object persistence.
- R2 outage does not create a document record.
- Normal user upload returns 403.

### US-10.2: View Documents by Access Level

**Backlog ID:** US-10.2  
**Issue type:** User Story (`type:user-story`)  
**Parent:** F10.4  
**Related feature IDs:** F10.5, F10.6  
**Depends on:** US-10.1, EPIC-04

#### Description

As a learner, I want to view permitted documents so that I can study reference material without bypassing access controls or receiving an application download action.

#### Action Items

- Filter document list/detail by access level at the API and storage boundary.
- Provide a view/open UI with temporary access and explicit loading/failure behavior.

#### Tasks

- [ ] Add paginated list/detail endpoints with public/restricted/admin authorization.
- [ ] Generate short-lived object access only after authorization.
- [ ] Add document viewer/open behavior without an application-level download button.
- [ ] Add access-matrix and expired-object-access tests.

#### Implementation Steps

1. Add paginated document list and detail endpoints.
2. Apply public/restricted/admin-only checks at API/service layers.
3. Generate short-lived authorized object access for permitted viewers.
4. Build viewer/open experience with loading and failure states.
5. Do not render an application-level Download button.

#### Acceptance Criteria
- Public documents are visible to everyone.
- Restricted documents require authentication.
- Admin-only documents are visible only to Super Admin.
- Unauthorized users receive no object URL or sensitive metadata.
- UI does not provide a Code Classic download action.

#### Test Scenarios
- Anonymous public document view succeeds.
- Anonymous restricted view returns 401.
- Authenticated user cannot view admin-only document.
- Expired temporary access is rejected and can be refreshed through authorization.
- Deleted document object cannot be retrieved through an old access request.

### US-10.3: Maintain Document Metadata and Lifecycle

**Backlog ID:** US-10.3  
**Issue type:** User Story (`type:user-story`)  
**Parent:** F10.3  
**Related feature IDs:** F10.1, F10.5  
**Depends on:** US-10.1, EPIC-04

#### Description

As a Super Admin, I want to update document metadata/access and remove obsolete documents so that the library stays accurate and stale links stop working.

#### Action Items

- Keep metadata and access changes authoritative on the server.
- Retire object references safely and report incomplete cleanup.

#### Tasks

- [ ] Add admin edit/delete operations and form validation.
- [ ] Apply access changes on the next authorized retrieval request.
- [ ] Delete or retire R2 objects safely and surface cleanup failures.
- [ ] Add tests for access change, stale links, deletion, and storage failure.

#### Implementation Steps

1. Add edit/delete admin operations.
2. Validate access-level changes against current visibility.
3. Invalidate cached list/detail data after mutations.
4. Delete/retire R2 object and metadata safely.
5. Document browser-level saving/screenshots as an unavoidable limitation.

#### Acceptance Criteria
- Only Super Admin can edit/delete documents.
- Access-level changes take effect on the next authorized request.
- Delete prevents future viewing and handles object cleanup safely.
- Stale object links do not bypass deletion/access rules.

#### Test Scenarios
- Change public to restricted and verify anonymous access stops.
- Delete document and verify list/detail/object access stops.
- R2 deletion failure is visible and does not silently claim full cleanup.
- Non-admin edit/delete is rejected.
