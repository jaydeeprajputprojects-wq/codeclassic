## 1. What We Built

US-00.1 creates the first runnable Code Classic slice:

```text
React + Vite frontend
        |
        | GET /api/v1/health
        v
Spring Boot backend
        |
        | JDBC + Flyway during startup
        v
PostgreSQL in Docker Compose
```

The frontend displays `Checking backend...`, `Connected`, or `Backend unavailable`. The backend returns a small safe response containing `status`, `service`, and `version`. PostgreSQL starts as a separate Docker service, and Flyway applies the baseline migration when Spring Boot starts.

The implemented files are documented in [README.md](../../README.md) and the source story is in [EPIC-00-Foundation.md](../user-stories/EPIC-00-Foundation.md).

## 2. User Story And Acceptance Criteria

### User Need

A developer should be able to clone the repository, follow documented commands, start PostgreSQL/backend/frontend, and see proof that the frontend can reach the real backend.

### Acceptance Criteria

- PostgreSQL, backend, and frontend start using documented setup.
- The frontend calls a real backend health/version endpoint.
- Invalid database configuration fails clearly without printing the password value.
- Restarting does not destructively rerun migrations.
- Tracked files contain no real credentials or tokens.

### Verification Status

The local runtime path was verified on 2026-09-30:

- PostgreSQL container reported healthy on port 5432.
- Flyway applied migration version 1 and later reported the schema up to date.
- Backend returned HTTP 200 from `/api/v1/health` on port 8081.
- Browser rendered `Connected` from `http://127.0.0.1:5173/`.
- A CORS preflight from the frontend origin returned HTTP 200.

The browser was run on port 8081 because an unrelated Apache `httpd` process already occupied port 8080. The default configuration still uses 8080 when that port is free.

## 3. Real Application Flow

### Startup Flow

1. Docker Compose creates or reuses the `postgres_data` named volume.
2. PostgreSQL starts with the database name and credentials supplied through environment substitution.
3. The health check runs `pg_isready` until PostgreSQL is ready.
4. Spring Boot starts on the configured server port.
5. Hikari creates a JDBC connection pool.
6. Flyway checks `flyway_schema_history`, validates migrations, and applies pending SQL files.
7. Spring MVC registers `HealthController`.
8. The backend begins accepting HTTP requests.
9. Vite serves the React application.

### Browser Request Flow

1. React renders the loading state.
2. `useEffect` calls `${apiBaseUrl}/api/v1/health`.
3. Spring CORS configuration checks the browser origin.
4. `HealthController.health()` creates a `HealthResponse` record.
5. Spring serializes the record to JSON.
6. React stores the JSON in `health` state.
7. JSX renders `Connected`, service name, status, and API version.
8. If fetch fails, the promise rejection sets `error` and renders a controlled message.

`@RequestMapping("/api/v1/health")` establishes the versioned resource path. `@GetMapping` maps a GET request to the `health()` method. The final `.catch()` intentionally hides implementation details and shows a controlled user-facing message.

## 6. Programming Language And Syntax

### Java

```java
@RestController
@RequestMapping("/api/v1/health")
public class HealthController {
```

- `@RestController` tells Spring that the class handles HTTP requests and return values become response bodies.
- `@RequestMapping` provides the base URL.
- `public class` defines a Spring-managed controller type.

```java
public record HealthResponse(String status, String service, String version) {
}
```

A `record` is a concise immutable data carrier. It automatically supplies accessors, a constructor, `equals`, `hashCode`, and `toString`. This is suitable for a small API response DTO.

```java
@GetMapping
public HealthResponse health() {
    return new HealthResponse("UP", "codeclassic-backend", applicationVersion);
}
```

`@GetMapping` connects HTTP GET to the method. The return type documents the response shape. `new` creates the DTO with safe values.

### Spring Property Injection

```java
@Value("${info.app.version:0.0.1-SNAPSHOT}")
```

`${property:default}` means use the configured property, or the fallback if absent. The version is configuration, not a hardcoded value inside the method logic.

### TypeScript and TSX

```typescript
type HealthResponse = {
  status: string;
  service: string;
  version: string;
};
```

This type describes the JSON expected from the backend. TypeScript checks usage during build, but it does not replace backend validation at runtime.

```typescript
const apiBaseUrl = import.meta.env.VITE_API_BASE_URL ?? 'http://localhost:8080';
```

`import.meta.env` reads Vite environment variables. The nullish coalescing operator `??` uses the local default only when the variable is missing or nullish.

```typescript
const [health, setHealth] = useState<HealthResponse | null>(null);
```

The generic type says the state is either a `HealthResponse` or `null`. The setter updates the state and causes React to render again.

```typescript
fetch(`${apiBaseUrl}/api/v1/health`)
```

A template literal inserts `apiBaseUrl` into the URL. This avoids hardcoding the full backend host in the component.

```typescript
return response.json() as Promise<HealthResponse>;
```

The type assertion tells TypeScript how the response is expected to be used. It does not validate malicious or malformed JSON; a production API client should add runtime validation if the contract becomes more complex.

### Maven XML

`pom.xml` uses XML elements to declare a parent, properties, dependencies, and plugins. For example, the Java property controls the compiler release, while dependency elements add Spring Boot Web, Actuator, JDBC, Flyway, PostgreSQL, and test libraries.

### Properties Configuration

```properties
spring.datasource.url=${DB_URL:jdbc:postgresql://localhost:5432/codeclassic}
spring.datasource.password=${DB_PASSWORD}
```

The URL has a safe local default. The password has no source-code default, so it must come from external configuration. This reduces the chance of accidentally embedding a real credential.

### Docker Compose YAML

```yaml
volumes:
  postgres_data:
```

This declares a named persistent volume. Container recreation does not automatically delete the database data.

```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
```

The list is a YAML sequence. `$${...}` escapes the dollar sign so Compose passes `${...}` into the container for shell expansion rather than expanding it too early.

YAML indentation is syntax. Tabs caused a Compose parser error; spaces fixed it.

### SQL Migration

```sql
CREATE TABLE IF NOT EXISTS app_metadata (...);

INSERT INTO app_metadata (key, value)
VALUES ('schema', 'baseline')
ON CONFLICT (key) DO NOTHING;
```

`IF NOT EXISTS` and `ON CONFLICT DO NOTHING` make the baseline safe for a local setup that may be repeated. Flyway still records the migration, so applied migration files should not be edited; a new version should be added instead.

### PowerShell

```powershell
Push-Location codeclassic\backend
mvn test
Pop-Location
```

`Push-Location` changes directory while preserving the previous location, and `Pop-Location` restores it. This matters because the terminal sometimes opened at the parent folder rather than the Git repository.

## 7. Object-Oriented Concepts

### Encapsulation

`HealthController` owns the details of converting a health request into a response. `HealthResponse` owns the response data. Callers do not manipulate internal controller state directly.

### Abstraction

Spring MVC abstracts HTTP server plumbing. The project code declares mappings and methods instead of manually parsing sockets. Flyway abstracts migration bookkeeping while the project still owns the SQL migration content.

### Dependency Injection

Spring injects the configured version into `HealthController` through `@Value`, and Spring creates the controller bean. This avoids manually constructing configuration-dependent objects in `main()`.

### Composition

The application is composed from Spring Boot, the controller, configuration, Flyway, Hikari, PostgreSQL, React, and Vite. Each part has a focused responsibility.

### Inheritance and Polymorphism

No meaningful custom inheritance hierarchy or polymorphic domain model was introduced for US-00.1. `WebConfig` implements Spring’s `WebMvcConfigurer` extension interface, but this is framework integration rather than a business inheritance design.

## 8. Design Principles And Project Standards

- **Separation of concerns:** Compose owns the database runtime, Flyway owns schema changes, Spring MVC owns HTTP mapping, and React owns browser rendering.
- **API versioning:** The route uses `/api/v1`, matching ADR-015.
- **DTO boundary:** The endpoint returns `HealthResponse`, not a JPA entity or unrestricted database row.
- **Externalized configuration:** Database credentials and ports come from environment variables.
- **Least exposure:** Actuator health details are hidden with `show-details=never`; the public health response contains no credentials or connection details.
- **Controlled failure:** The frontend catches fetch errors and renders a message instead of allowing an unhandled promise rejection to define the UI.
- **Persistent local data:** The named Docker volume supports restart without destructive schema recreation.
- **Smallest useful architecture:** No generic service layer, Redis, Kafka, gateway, or future product module was added solely for hypothetical needs.
- **Accessibility:** The status section uses `aria-live="polite"` so state changes can be announced without aggressively interrupting the user.
- **Security boundary:** Hiding frontend content is not authorization. Backend authorization will be required when protected features are added.

## 10. Why This Approach

US-00.1 is a foundation story, so the useful proof is a thin vertical path rather than a large architecture. The frontend calls a real endpoint, the backend starts against a real PostgreSQL container, and Flyway proves the database schema can be created reproducibly.

Spring Boot fits the accepted backend ADR because it provides application startup, dependency wiring, web routing, Actuator, JDBC integration, and Flyway integration. React/Vite fits the frontend ADR and keeps the first browser flow easy to inspect. PostgreSQL is appropriate because the platform will later contain relational users, blogs, comments, jobs, courses, and documents.

The response is intentionally small. It proves connectivity without exposing database internals or creating a premature domain model.

## 11. Alternatives And Trade-Offs

The following alternatives were considered conceptually; they were not all executed in this session.

| Alternative | Benefit | Cost | Why current choice fits |
|---|---|---|---|
| Hibernate `ddl-auto=update` instead of Flyway | Very little migration setup. | Schema changes become less explicit and harder to audit safely. | Flyway is an accepted project decision and gives versioned SQL. |
| SQLite instead of PostgreSQL | Easier single-file setup. | Does not represent the selected production relational database or PostgreSQL behavior. | PostgreSQL is the selected primary database. |
| Backend and PostgreSQL inside Compose | One command could start more services. | Adds image/build complexity before the baseline is stable. | F00.1 explicitly requires PostgreSQL-only Compose. |
| Redux/global state for one health request | Centralized state pattern. | Unnecessary complexity for one server response. | Local React state is enough for this slice. |
| Hardcoded API host | Simple first implementation. | Fails when ports/environments change and encourages production host leakage. | Vite environment configuration keeps the host adjustable. |
| Allow all CORS origins | Avoids local hostname mismatch. | Weakens the browser boundary and is unsafe as a general policy. | Explicit configured/local origins are narrower. |
| One application-level health endpoint only | Simple response. | Does not expose operational dependency detail. | The app endpoint is stable for the frontend and Actuator is available for operations. |

## 12. Interview Questions: Around 1 Year Experience

### Question 1: How does the frontend know whether the backend is working?

**Sample answer:** `App.tsx` calls `/api/v1/health` inside `useEffect`. If the response is successful, it stores the typed JSON in `health` and renders `Connected`. If the request fails, it stores an error message and renders `Backend unavailable`.

**Likely follow-up:** What happens while the request is still running?  
**Answer:** Both state values are initially empty, so the component renders `Checking backend...`.

### Question 2: What does Flyway do here?

**Sample answer:** Flyway runs versioned SQL migrations against PostgreSQL during Spring Boot startup. It records executed versions in `flyway_schema_history`, so already-applied migrations are not run again.

**Likely follow-up:** How would you change the schema after V1?  
**Answer:** Add a new migration such as `V2__create_users_table.sql`; do not edit the already-applied V1 file.

### Question 3: Why is the password in environment configuration?

**Sample answer:** A password should not be committed in Java, Compose, or the README. The application reads `DB_PASSWORD` from the process environment, while `.env` is ignored by Git.

**Likely follow-up:** Is the frontend allowed to receive the database password?  
**Answer:** No. The frontend only receives public API responses. Database credentials belong to the backend runtime.

### Question 4: What does `@GetMapping` do?

**Sample answer:** It tells Spring MVC to call the annotated method for an HTTP GET request under the controller’s base path. Here the complete endpoint is `/api/v1/health`.

**Likely follow-up:** Why return a DTO instead of a database entity?  
**Answer:** A DTO controls the public response shape and prevents accidental exposure of persistence fields.

## 13. Interview Questions: Around 6 Years Experience

### Question 1: Is an application health endpoint enough for production readiness?

**Sample answer:** No. This endpoint proves the application route is responding, while Actuator and infrastructure health should provide dependency and operational signals. The public response should remain sanitized, and readiness/liveness policy should be made explicit before production deployment.

**Follow-up probes:** How would you distinguish database-down from application-up? What should be public versus operator-only?  
**Answer:** Use separate readiness/dependency indicators and restrict detailed dependency output to internal monitoring or secured Actuator access.

### Question 2: What are the migration risks of Flyway in a multi-instance deployment?

**Sample answer:** All instances may start near the same time, so migration locking, backward-compatible changes, and deployment ordering matter. The migration should be small, reviewed, and compatible with the application versions that may temporarily coexist.

**Follow-up probes:** How would you handle a failed migration?  
**Answer:** Stop rollout, inspect Flyway history and database state, repair only with a controlled operational procedure, and add a corrective migration rather than silently editing history.

### Question 3: Why not allow `*` for CORS during local development?

**Sample answer:** Broad CORS can hide origin mistakes and may be copied into production. Explicit local origins reproduce the intended browser boundary and keep accidental exposure smaller.

**Follow-up probes:** What changes if credentials or cookies are introduced?  
**Answer:** CORS origin rules, allowed headers, credentials policy, CSRF protection, and backend authorization must be reviewed together; frontend visibility is not a security control.

### Question 4: What does the current local port workaround tell you operationally?

**Sample answer:** Port conflicts are environment configuration, not application behavior. The backend port and frontend API base must be configurable, and the setup guide should explain how to override both consistently.

**Follow-up probes:** Would you commit 8081 as the permanent default?  
**Answer:** Not without a project decision. First determine whether 8080 is a team-wide conflict or only local to this machine, then document one standard default plus an override.

## 14. Cross-Questions And Follow-Ups

### Successful Path

**Question:** The browser shows `Connected`. What did that prove?  
**Follow-up:** Does it prove every database query in the future will work?  
**Grounded answer:** It proved the frontend reached the backend health route and the backend started with a successful PostgreSQL/Flyway connection. It does not prove future business queries, authorization, performance, or all migrations.

### Database Failure

**Question:** What happens if PostgreSQL is unavailable?  
**Follow-up:** Should the frontend still show `Connected` because the Java process is alive?  
**Grounded answer:** In this implementation, Flyway/JDBC startup fails when the database cannot be reached, so the backend does not complete startup. The frontend should show its controlled unavailable state. A later readiness design may separate process liveness from dependency readiness.

### Credential Failure

**Question:** What happened when the database password was wrong?  
**Follow-up:** How do you prove the password was not leaked?  
**Grounded answer:** Spring/Flyway reported authentication failure without displaying the password value. Verification should inspect logs and tracked files, while avoiding printing environment values in troubleshooting output.

### CORS Security

**Question:** Why did direct PowerShell API testing pass while the browser failed?  
**Follow-up:** Which layer rejected the request?  
**Grounded answer:** The server route was healthy, but the browser enforced the same-origin policy and rejected the response because `127.0.0.1:5173` was not initially allowed. The fix was to allow explicit local origins in Spring configuration.

### Migration Safety

**Question:** Why does the migration use `IF NOT EXISTS`?  
**Follow-up:** Does that alone make all migrations safe?  
**Grounded answer:** It makes this baseline tolerant of a repeated local setup, but migration safety also depends on versioning, transaction behavior, constraints, data compatibility, and careful review.

## 18. PostgreSQL And Docker: Beginner Setup Guide

This section explains the local database setup for a developer who is new to PostgreSQL and Docker.

### 18.1 What PostgreSQL Is

PostgreSQL is a relational database management system. It stores structured data in tables and supports primary keys, foreign keys, constraints, SQL queries, transactions, users, and permissions.

Code Classic uses PostgreSQL because future features will relate users, blogs, comments, jobs, courses, documents, likes, and approvals. A relational database fits these relationships.

| Concept | Meaning |
|---|---|
| Server | The running PostgreSQL process accepting connections. |
| Database | A named container for schemas and tables, here `codeclassic`. |
| Schema | A namespace inside a database, commonly `public`. |
| Table | Structured storage made of rows and columns. |
| Role/user | An identity used to connect and receive permissions. |
| Port | The network address used by clients; PostgreSQL commonly uses 5432. |
| Transaction | A group of changes committed together or rolled back together. |

### 18.2 What Docker Is

Docker packages an application and its runtime environment into a container. A container is an isolated process, not a full virtual machine. It keeps files, processes, and networking separate from the host while using the host operating system kernel.

| Term | Beginner meaning |
|---|---|
| Image | A read-only packaged template, such as `postgres:16-alpine`. |
| Container | A running instance created from an image. |
| Registry | A place from which images are downloaded, commonly Docker Hub. |
| Volume | Persistent storage managed outside the container lifecycle. |
| Network | A private communication area for containers. |
| Compose | YAML-based configuration for related containers. |
| Service | A Compose definition describing how to run a container. |

```text
Image     -> template
Container -> running process created from the template
Volume    -> persistent data kept separately from the container
```

Deleting a container does not necessarily delete a named volume. That is why database data can survive a stop and recreate operation.

### 18.3 Why Use Docker For PostgreSQL

PostgreSQL can run directly on Windows, but Docker gives this project a reproducible local environment:

- A fixed PostgreSQL major version: `postgres:16-alpine`.
- No host-level PostgreSQL installer or Windows service configuration.
- The same database setup for every contributor.
- A disposable container independent of host installation details.
- A named volume for persistent local data.
- A health check for database readiness.
- A configuration file that can be reviewed in Git.

Docker does not change the PostgreSQL protocol. The application still connects normally:

```text
jdbc:postgresql://localhost:5432/codeclassic
```

From Spring Boot's perspective, PostgreSQL can be native or containerized. It only sees a PostgreSQL server at the configured host and port.

### 18.4 PostgreSQL In Docker Compose

The project uses [docker-compose.yml](../../docker-compose.yml):

```yaml
services:
  postgres:
    image: postgres:16-alpine
    container_name: codeclassic-postgres
    restart: unless-stopped
    environment:
      POSTGRES_DB: ${POSTGRES_DB:-codeclassic}
      POSTGRES_USER: ${DB_USERNAME:-codeclassic}
      POSTGRES_PASSWORD: ${DB_PASSWORD:?Copy .env.example to .env and set DB_PASSWORD}
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 5s
      timeout: 5s
      retries: 10

volumes:
  postgres_data:
```

The important syntax is:

- `services` contains the managed services.
- `postgres` is the service name.
- `image` selects the PostgreSQL image and version.
- `environment` passes initialization settings to the official image.
- `ports` maps host port 5432 to container port 5432. The left side is the host; the right side is the container.
- `volumes` mounts persistent storage at PostgreSQL's data directory.
- `healthcheck` runs `pg_isready` until PostgreSQL accepts connections.
- `interval`, `timeout`, and `retries` control health-check behavior.
- The root `volumes` block declares the named volume.

YAML indentation is syntax. Tabs caused a Compose parser error during this setup; spaces fixed it.

### 18.5 Password And Environment Flow

The password moves through two startup paths:

```text
.env
  |
  | Docker Compose variable interpolation
  v
POSTGRES_PASSWORD inside PostgreSQL container

.env or process environment
  |
  | Spring property resolution
  v
spring.datasource.password -> JDBC connection -> PostgreSQL
```

The tracked [`.env.example`](../../.env.example) contains variable names and a safe local placeholder. The ignored `.env` is the developer's local copy. Never commit `.env`.

Docker Compose reads `.env` automatically for Compose variable substitution. Maven and Spring Boot do not automatically read a `.env` file in a plain PowerShell process. In this session, the backend was started with the database variables explicitly assigned to the process.

The password must match the password stored when PostgreSQL initialized its data directory. Changing `.env` after the named volume exists does not change the PostgreSQL role password.

For a disposable database, recreate the volume after changing the password:

```powershell
docker compose down -v
docker compose up -d postgres
```

`down -v` deletes the local database volume and its data. Do not use it when the data must be preserved. For preserved data, change the role password inside PostgreSQL using an authenticated SQL session.

### 18.7 Useful Docker Commands

```powershell
# Start PostgreSQL in the background
docker compose up -d postgres

# Show running Compose services
docker compose ps

# Show PostgreSQL logs
docker compose logs postgres

# Follow PostgreSQL logs
docker compose logs -f postgres

# Stop containers but keep the named volume
docker compose down

# Stop containers and delete named volumes; destructive for local data
docker compose down -v

# List all containers
docker ps -a

# Open psql inside the PostgreSQL container
docker exec -it codeclassic-postgres psql -U codeclassic -d codeclassic
```

The `-d` option means detached/background mode. The `-f` option follows logs. The `-v` option on `docker compose down` removes named volumes and is destructive for local data.

### 18.8 Useful PostgreSQL Commands

Inside the `psql` prompt:

```sql
-- List databases
\l

-- List tables in the current database
\dt

-- Describe a table
\d app_metadata

-- Show Flyway migration history
SELECT installed_rank, version, description, success
FROM flyway_schema_history
ORDER BY installed_rank;

-- Read the baseline row
SELECT key, value FROM app_metadata;

-- Exit psql
\q
```

Commands beginning with a backslash are `psql` meta-commands. The `SELECT` statements are standard SQL.

The migration query for this story returned:

```text
installed_rank | version | description           | success
1              | 1       | create local baseline | t
```

This confirms that Flyway executed version 1 successfully.

### 18.9 How PostgreSQL Connects To Spring Boot

The relevant settings are in [application.properties](../../backend/src/main/resources/application.properties):

```properties
spring.datasource.url=${DB_URL:jdbc:postgresql://localhost:5432/codeclassic}
spring.datasource.username=${DB_USERNAME:codeclassic}
spring.datasource.password=${DB_PASSWORD}
spring.flyway.enabled=true
```

Spring Boot creates a `DataSource` from these values. HikariCP manages a connection pool. Flyway uses the same connection information to validate and apply migrations.

The JDBC URL means:

```text
jdbc:postgresql://localhost:5432/codeclassic
 |       |          |          |
 |       |          |          database name
 |       |          PostgreSQL port
 |       database host
 JDBC driver protocol
```

When the backend runs on the host, `localhost` means the Windows machine, and Docker's port mapping forwards it to the container. If the backend later runs inside Compose, it should normally use the service hostname `postgres` instead of `localhost`.

### 18.10 Docker Networking: Host And Container Views

```text
Backend on Windows host -> localhost:5432 -> published Docker port -> PostgreSQL container

Backend in Compose network -> postgres:5432 -> PostgreSQL service directly
```

Do not use `localhost` to refer to another container from inside a container. Inside a container, `localhost` means that same container. Use the Compose service name for container-to-container communication.

### 18.11 Flyway And PostgreSQL Together

Flyway is not a replacement for PostgreSQL. PostgreSQL stores data; Flyway controls schema changes.

At backend startup:

1. Spring resolves database configuration.
2. JDBC connects to PostgreSQL.
3. Flyway looks for `flyway_schema_history`.
4. Flyway validates migration files.
5. Flyway runs pending files such as `V1__create_local_baseline.sql`.
6. Flyway records the version and success status.
7. Spring finishes startup.

For a future schema change, create a new file such as `V2__create_users_table.sql`. Do not edit an applied migration because that can create checksum mismatches or make environments disagree about history.

### 18.12 Native PostgreSQL Alternative

Docker is a project choice, not a PostgreSQL requirement. PostgreSQL can be installed directly on Windows.

With native PostgreSQL, the developer must manage the PostgreSQL version, Windows service, `codeclassic` database, `codeclassic` role, password, port 5432, local data directory, service startup, and backups.

The Spring Boot JDBC URL can remain the same:

```text
jdbc:postgresql://localhost:5432/codeclassic
```

Native PostgreSQL can make sense when Docker is not allowed, the developer already manages PostgreSQL locally, or the team has a standard native installation. Docker is preferable for this learning project because a clean checkout uses one documented setup instead of undocumented host state.

### 18.13 Other Alternatives

| Alternative | When it can make sense | Trade-off for this project |
|---|---|---|
| Native PostgreSQL | Existing local database or Docker restriction. | More manual setup and version drift. |
| PostgreSQL in WSL | Linux-focused development environment. | Adds WSL networking and service management. |
| Podman | Docker-compatible rootless workflow. | Requires a different runtime and team agreement. |
| Testcontainers | Automated integration tests with disposable databases. | Excellent for tests, but not the daily development database yet. |
| Managed PostgreSQL | Shared or production-like environment. | Requires network, credentials, cost, and stronger data controls. |
| SQLite | Very small prototypes. | Does not match the selected PostgreSQL production path exactly. |

Testcontainers is a likely future testing choice under the accepted testing strategy, but it was not implemented in US-00.1.

### 18.14 Common Beginner Problems

#### `docker` is not recognized

Docker may be installed but missing from the current terminal PATH. Restart VS Code or add Docker Desktop's executable directory to the current PowerShell process.

#### Docker engine pipe is missing

Docker Desktop is installed but its engine is not running. Open Docker Desktop and wait until its engine reports running.

#### Credential helper is missing

The Docker CLI may find `docker.exe` but not `docker-credential-desktop.exe`. Add Docker Desktop's resources directory to PATH for the current process.

#### YAML scanner error at line 2

Check for tabs. YAML mappings must use spaces consistently.

#### Port 5432 is already in use

Another PostgreSQL service may be running. Identify the process before changing ports. If changing the host port, update `DB_URL` while keeping the container port 5432.

#### Password authentication failed

Check that the backend process password matches the password used when the PostgreSQL volume was initialized. Changing `.env` alone does not change an existing role password.

#### Backend starts but frontend says unavailable

Check the backend `SERVER_PORT`, frontend `VITE_API_BASE_URL`, and backend `FRONTEND_URL`/CORS origin together. Also distinguish `localhost` from `127.0.0.1`; browsers treat them as different origins.

#### Flyway checksum or migration error

Do not edit an applied migration casually. Inspect `flyway_schema_history`, compare the migration file with the applied version, and add a corrective migration through a controlled process.

### 18.15 Security Learning Rules

- Keep `.env` ignored by Git.
- Put only safe placeholders in `.env.example`.
- Never print passwords in terminal logs.
- Never send database credentials to the frontend.
- Do not expose PostgreSQL to the public internet.
- Use separate development, test, and production credentials.
- Use least-privilege database users in production.
- Use encrypted connections where the production provider requires them.
- Treat `docker compose down -v` as data-destructive.
- Keep database backups separate from migration files.

### 18.16 Beginner Learning Path

1. Start and stop the PostgreSQL container.
2. Read `docker compose ps` and `docker compose logs postgres`.
3. Open `psql` and inspect `app_metadata`.
4. Read the Flyway history table.
5. Start the backend and read the migration log.
6. Call `/api/v1/health` directly.
7. Open the frontend and observe `Connected`.
8. Stop the backend and observe the controlled frontend error.
9. Restart the backend and confirm the migration is not applied again.
10. Add a harmless V2 migration in a practice branch and inspect the new history row.

This sequence teaches infrastructure, database, migration, backend, API, browser, and troubleshooting concepts in the same order that the request flows through the system.
